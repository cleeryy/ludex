# PostgreSQL backend

Ludex runs on SQLite by default: one file, no external service, nothing to
operate. Since #46 the same server can use PostgreSQL instead, which is aimed at
operators who already run a database server (backups, replication, monitoring,
shared storage) or who want the library database outside the container volume.

The backend is chosen at startup from `LUDEX_DATABASE_URL`:

| URL | Backend |
|---|---|
| `sqlite:///data/ludex.db?mode=rwc` (default) | SQLite |
| `postgres://ludex:secret@db:5432/ludex` | PostgreSQL |
| `postgresql://…` | PostgreSQL |

SQLite stays the default and the only backend used by the desktop app.

## Quick start (Docker Compose)

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ludex
      POSTGRES_PASSWORD: change-me
      POSTGRES_DB: ludex
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ludex -d ludex"]
      interval: 5s
      timeout: 3s
      retries: 20

  ludex:
    image: ghcr.io/cleeryy/ludex:latest
    environment:
      LUDEX_DATABASE_URL: postgres://ludex:change-me@postgres:5432/ludex
      # Optional pool ceiling; default 8.
      LUDEX_DATABASE_MAX_CONNECTIONS: "10"
    depends_on:
      postgres:
        condition: service_healthy

volumes:
  pgdata:
```

Without Compose, on a host:

```bash
export LUDEX_DATABASE_URL='postgres://ludex:secret@127.0.0.1:5432/ludex'
ludex-server
```

Startup fails fast with an explicit error when the server is unreachable, the
credentials are wrong, or the role cannot create tables in the target schema.
The password never appears in logs: URLs are redacted before being printed or
embedded in errors.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `LUDEX_DATABASE_URL` | `sqlite://$LUDEX_DATA_DIR/ludex.db?mode=rwc` | Connection string. `postgres://` selects PostgreSQL. |
| `LUDEX_DATABASE_BACKEND` | inferred from the URL | `sqlite` or `postgres`. Only needed when the URL has no scheme (for example a bare path or `host/db`). A value that contradicts the URL is a startup error. |
| `LUDEX_DATABASE_MAX_CONNECTIONS` | `8` | Pool ceiling for either backend. Raise it for PostgreSQL when many requests block on the database; each connection costs memory on the server (`work_mem`, etc.). |

`/data` is still required in PostgreSQL mode: it holds the generated JWT secret,
save archives, uploads and media. The library database itself lives in
PostgreSQL.

### Recommended PostgreSQL settings

- PostgreSQL 14 or newer (tested on 16).
- The role needs `CREATE` on the target schema for the first start (migrations
  create the tables, indexes and `_sqlx_migrations`).
- If you use a connection pooler (PgBouncer), keep the session mode or disable
  prepared-statement caching in the pooler; Ludex uses prepared statements via
  `sqlx`.
- Back up with `pg_dump` (see below), not by copying files.

## Schema and migrations

`crates/ludex-server/migrations_postgres/` mirrors `migrations/` (SQLite) version
for version: `0001` … `0019`, same table names, same `_sqlx_migrations`
bookkeeping. The server selects the directory from the backend and applies
pending migrations at startup, under a lock, exactly like SQLite.

Type mapping:

| SQLite | PostgreSQL |
|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `INTEGER` (counters, ids, boolean flags) | `BIGINT` |
| `REAL` | `DOUBLE PRECISION` |
| `TEXT` (timestamps, JSON, hashes) | `TEXT` |
| `BLOB` | `BYTEA` (none in the current schema) |

Timestamps stay RFC 3339 UTC **text** and JSON stays **text**. That is
deliberate: the server binds plain `i64`/`f64`/`String` values and reads the same
types from both engines, so one query text stays valid everywhere. Booleans are
`BIGINT` `0/1` because every row struct already reads them as `i64` — switching
them to `BOOLEAN` would fork every struct and query.

## Query compatibility

All queries go through a small database layer (`crates/ludex-server/src/db.rs`)
that owns both pools and rewrites `?` placeholders to `$1, $2, …` for
PostgreSQL (string literals, quoted identifiers and comments are skipped). The
SQL is otherwise written once and runs on both engines. Where the dialects
really differ, the code branches on the backend:

| Concern | SQLite | PostgreSQL |
|---|---|---|
| Genre filter (`?genre=`) | `json_each(genres_json)` | `jsonb_array_elements_text(genres_json::jsonb)` |
| Case-insensitive sort | `COLLATE NOCASE` | `lower(column)` |
| Case-insensitive unique collection name | `UNIQUE(user_id, name COLLATE NOCASE)` | unique expression index on `(user_id, lower(name))` |
| `SUM(bigint)` | integer | `NUMERIC` → wrapped in `CAST(… AS BIGINT)` |
| Scalar `MAX(a, b)` | two-argument `MAX` | `CASE WHEN a > b THEN a ELSE b END` |
| Generated ids | `RETURNING id` (SQLite 3.35+) | `RETURNING id` |
| Boolean columns | `INTEGER` | `BIGINT` |

`crates/ludex-server/tests/postgres.rs` exercises migrations, setup, login, the
game list and filters, stats, collections (including the case-insensitive
unique index), API keys, audit log, community feed, suggestions, library roots,
integrity reports, media GC, shares, news, metadata-provider and OIDC settings,
emulators, controller profiles, cloud saves and logout against a real
PostgreSQL server.

### Known behavioural differences

- **NULL ordering**: PostgreSQL sorts `NULL`s last for `ASC`; SQLite sorts them
  first. Sorting by a nullable column (`releaseDate`, `lastPlayed`) can therefore
  order unset rows differently. Nothing breaks; the pagination totals stay
  correct.
- **Case-insensitive matching**: SQLite `LIKE` is case-insensitive for ASCII,
  PostgreSQL `LIKE` is case-sensitive. The server only uses `LIKE` for the
  external GOG achievement database (SQLite-only path) and for metadata search,
  where the pattern is already lowered on both sides.
- **`ILIKE`-free text search** is unchanged: searches use `lower(column) LIKE
  lower(?)`, identical on both engines.

## Health and metrics

`GET /api/health/details` gained fields (additive, no breaking change):

```json
"database": {
  "ok": true,
  "backend": "postgres",
  "sizeBytes": 12345678,
  "connections": 3,
  "idleConnections": 2,
  "maxConnections": 10
}
```

`sizeBytes` is `pg_database_size(current_database())` on PostgreSQL (0 when the
server refuses the query) and the SQLite file plus WAL on SQLite.
`ludex_database_size_bytes` in `/metrics` follows the same rule.

## Backup and restore

`ludex-backup` only handles SQLite: its archive contains a `VACUUM INTO`
snapshot of `ludex.db`. On PostgreSQL:

- `ludex-backup backup` **refuses** with an explicit message;
- `ludex-backup restore` **refuses** as well.

Use the PostgreSQL tooling instead:

```bash
# backup (custom format, compressed)
pg_dump --format=custom --no-owner --no-acl \
  --file=ludex-$(date +%F).dump "$LUDEX_DATABASE_URL"

# restore into an empty database
pg_restore --no-owner --no-acl --dbname="$LUDEX_DATABASE_URL" ludex-2026-11-11.dump
```

Keep `/data` (JWT secret, saves, uploads) and `/games` in your file backups. A
restored database paired with a different `jwt.secret` invalidates existing
sessions (users sign in again) and makes the stored OIDC client secret
undecryptable — restore the data directory together with the dump.

## Moving from SQLite to PostgreSQL

There is **no in-place conversion** in this release. Two supported paths:

1. **Fresh start (simplest).** Point `LUDEX_DATABASE_URL` at PostgreSQL and let
   the scanner rebuild the library on first boot. The archives are re-indexed
   and metadata is fetched again; accounts, progress, saves and manual metadata
   edits are not carried over (save archives on disk stay, but their database
   rows do not).
2. **Copy the data (keep accounts/progress).** Snapshot SQLite first with
   `ludex-backup backup --output /backups/pre-postgres.tar.gz` (this is the
   rollback point), let Ludex create the PostgreSQL schema, then copy rows with
   a third-party tool such as
   [pgloader](https://pgloader.readthedocs.io/):

   ```bash
   # 1. rollback point
   ludex-backup backup --output /tmp/pre-postgres.tar.gz
   mkdir /tmp/pre-postgres && tar -xzf /tmp/pre-postgres.tar.gz -C /tmp/pre-postgres

   # 2. create the exact PostgreSQL schema: start the server once on the empty
   #    database, wait for the "database ready" log line, then stop it

   # 3. copy rows only: the tables and constraints already exist
   pgloader --with "quote identifiers" --with "data only" \
     sqlite:///tmp/pre-postgres/ludex.db \
     "$LUDEX_DATABASE_URL"
   ```

   Start Ludex on PostgreSQL and verify counts (`SELECT COUNT(*) FROM games`,
   `FROM users`, `FROM save_snapshots`). Keep the archive until the new
   deployment is validated. Identity sequences are not copied by pgloader; run
   `SELECT setval(pg_get_serial_sequence('games', 'id'), COALESCE(MAX(id), 1))
   FROM games;` (same for `users`, `game_versions`, the other tables with an
   `id`) so inserts do not reuse existing ids.

Downgrading is the reverse: stop the server, restore the SQLite snapshot over
`/data/ludex.db`, unset `LUDEX_DATABASE_URL`.

## Limitations

- `ludex-backup` does not back up or restore PostgreSQL (by design, documented
  above). Use `pg_dump`/`pg_restore`.
- The desktop app always uses SQLite. `LUDEX_DATABASE_URL` is a server/CLI
  setting; the in-process server in the desktop build ignores overrides.
- `PRAGMA`-based maintenance (WAL checkpoint, `VACUUM`) does not exist on
  PostgreSQL and is not attempted. PostgreSQL autovacuum handles it.
- No automatic SQLite → PostgreSQL data migration (see above).
- S3/object-storage, media cache, saves and uploads are backend-independent and
  unchanged.
- Two servers must not share one SQLite file; with PostgreSQL they can share the
  database (migrations use an advisory lock at startup), but the current release
  is still designed around one active server per deployment.
