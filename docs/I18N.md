# Internationalisation and themes

Ludex ships English and French as official locales, plus community-seeded
German, Spanish and Arabic. The web client also has light, dark and system
themes, an installable PWA shell and an offline fallback. This document is the
contribution guide for both.

## How the web client translates

English is the source language, so **the English message is the message id**
(the same model as gettext `msgid`). Source code calls `t("…")` with the exact
English copy; locale JSON files map that id to a translation. Missing entries
fall back to the English id, which means a partially translated locale is
always usable and never shows a raw key.

The runtime lives in [`apps/web/src/lib/i18n.tsx`](../apps/web/src/lib/i18n.tsx).
`apps/web/scripts/i18n.mjs` owns the catalog: it extracts every message id from
`t()`, `tn()` and `tr()` calls, writes `en.json`, checks key parity and keeps
`coverage.json` up to date.

```
apps/web/src/locales/
  manifest.json    locale registry: code, native name, direction, status, Intl tag
  en.json          generated identity catalog (one key per UI string)
  fr.json          official translation, must stay at 100 %
  de.json          community seed, partial and falling back to English
  es.json          community seed
  ar.json          community seed, RTL, machine-seeded and unreviewed
  coverage.json    generated per-locale coverage, shown in Settings
```

### The three helpers

```tsx
import { t, tn, tr } from "@/lib/i18n";

t("Library");
t("Last played {when}", { when: formatRelative(game.lastPlayedAt) });
tn(count, "1 game", "{count} games");
tr("{who} added {game} to the library", { who, game: gameLink });
```

- `t(id, vars?)` interpolates `{name}` placeholders. Numbers are formatted with
  `Intl.NumberFormat` for the active locale.
- `tn(count, one, other, vars?)` chooses the plural form with
  `Intl.PluralRules`. Translators can add `|category` entries keyed on the
  plural message id, e.g. `"{count} games|one": "{count} jeu"` or the Arabic
  `|zero`, `|two`, `|few`, `|many`, `|other` variants.
- `tr(id, vars)` is the rich-text variant: values may be React nodes, so a
  sentence can keep its inline links and code spans while translators reorder
  the sentence.

Interpolation placeholders must match between English and every translation;
the checker enforces this. Do not translate message ids, code spans, product
names, file names or environment variable names.

### Changing copy or adding a string

1. Wrap the copy in `t("…")` (or `tn`/`tr`) in the component. For JSX text, the
   expression form is `{t("…")}`; for attributes use `label={t("…")}`.
2. Run `pnpm --filter @ludex/web i18n:write`. This regenerates `en.json` and
   `coverage.json` and prints the per-locale coverage table.
3. Add the French translation to `fr.json` (the checker fails if it is
   missing). Community locales may stay partial.
4. Run `pnpm --filter @ludex/web i18n:check` (also part of `check` and
   `build`).

Never edit `en.json` or `coverage.json` by hand: both are generated.

### CI gate

`pnpm --filter @ludex/web i18n:check` fails when:

- source copy is not in `en.json` (forgot `i18n:write`);
- `en.json` has stale ids that no longer exist in source;
- an official locale (`en`, `fr`) is missing a translation;
- any locale has an empty value, an unknown id, or mismatched `{placeholders}`;
- `coverage.json` is stale.

`--strict` additionally requires 100 % coverage from every locale. It is not
part of the default build: community locales are allowed to be partial and fall
back to English. Warnings report community locales below 10 %.

## Adding a locale without touching TypeScript

A community translator can add a language with two JSON files only:

1. Copy `en.json` to `src/locales/xx.json` and translate values. Start with the
   navigation, settings, library, downloads and empty-state strings; everything
   else falls back to English.
2. Add an entry to `src/locales/manifest.json`:

```json
{
  "code": "pt-BR",
  "label": "Português (Brasil)",
  "englishLabel": "Portuguese (Brazil)",
  "dir": "ltr",
  "status": "community",
  "reviewed": false,
  "intl": "pt-BR"
}
```

3. Run `pnpm --filter @ludex/web i18n:write` to refresh coverage, then
   `pnpm --filter @ludex/web check`.

The locale appears in Settings under **Community translations** immediately;
locale chunks are lazy-loaded by Vite through `import.meta.glob`, so the new
file is discovered at build time without editing the registry code. For a
right-to-left language set `"dir": "rtl"` and make sure the RTL checks below
pass. Set `"reviewed": true` and `"status": "official"` only after a native
review; official locales are required to be complete by the CI gate.

Arabic (`ar.json`) is deliberately marked `community`/unreviewed: it was
machine-seeded to prove the RTL path and needs a native review before it can be
called official.

## RTL rules

- The document direction is set before the first paint from the stored locale
  (`index.html` inline boot script) and kept in sync by `I18nProvider`.
- New layout code uses logical properties: `ps-*`/`pe-*`, `ms-*`/`me-*`,
  `start-*`/`end-*`, `text-start`/`text-end`, `border-s`/`border-e`.
- Older screens still contain physical helpers (`ml-auto`, `pl-3`, `left-2`,
  `border-l-2`). `styles/index.css` contains a deliberately small `[dir="rtl"]`
  bridge for those classes. New code must not add physical helpers.
- Directional icons (back/next arrows, chevrons) carry `rtl:-scale-x-100`.
- Dates, numbers, relative times and plural categories go through
  `Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.RelativeTimeFormat` and
  `Intl.PluralRules`; never hand-format a date.
- Arabic falls back to the system Arabic font because the Latin display faces
  have no Arabic glyphs.

Manual RTL smoke: choose العربية in Settings, reload, and check at 390 px that
`document.documentElement.dir === "rtl"`, the page has no horizontal overflow,
the mobile tab bar is reachable, and every arrow points the right way.

## Themes

Themes are client preferences (`light`, `dark`, `system`) stored in
`localStorage["ludex.theme"]` and exposed in Settings → Appearance. Dark is the
default and the primary design. `index.html` applies the stored theme before
the first paint; `SettingsProvider` applies it on change and follows
`prefers-color-scheme` while `system` is selected. The only light-mode work was
a token set in `styles/index.css` plus contrast fixes; layout and component
styling are unchanged.

`src/styles/tokens.test.ts` parses the token blocks and enforces WCAG AA
(4.5:1) for the text/background pairs used by the UI in dark, light and the
`force-dark` game-detail stage. Add a pair there when introducing a new
foreground/background combination.

## PWA and offline

- `public/manifest.webmanifest` declares the name, standalone display, theme
  colours, maskable 192/512 icons and shortcuts.
- `public/sw.js` is versioned by a content hash injected at build time
  (`vite.config.ts`). It precaches the shell (HTML, CSS, JS, fonts, icons,
  manifest and `offline.html`) and deletes old `ludex-*` caches on activate.
- Navigation is network-first with the cached shell as fallback. Static assets
  are cache-first. Only the public `/api/media/` image cache is cached; every
  other `/api/` request (including auth and JSON) goes straight to the network.
- A waiting worker never activates on its own: the shell shows **Reload now**
  and posts `SKIP_WAITING` on click.
- Install prompt is deferred, dismissible for 30 days
  (`localStorage["ludex.pwa.installDismissedAt"]`).
- All locale JSON chunks are precached, so switching language offline works
  after the first visit.
- `public/offline.html` is the last-resort page when the shell cache is empty.

The service worker is registered only in production builds
(`import.meta.env.PROD`); `vite dev` never serves a stale shell. To smoke it:

```bash
pnpm --filter @ludex/web build
pnpm --filter @ludex/web preview --host 127.0.0.1 --port 4174
# open http://127.0.0.1:4174, wait for the worker, then reload with DevTools
# Network set to Offline; the shell (or offline.html) must render.
```
